# The alert

The island's unprompted expansion: what opens the card by itself, what owns the fold while it is open, and the three ways it ends.

**The island is the reminder surface whenever the bubble is off.** `AppDelegate.showBubble` routes the bubble's two transitions here: `IslandHost.alert(name:kind:pid:seconds:)` (`IslandAlertKind.waiting`/`.ready`) opens the card on **every** screen's panel, marks the transitioning session's row with a 3pt rule in the row's leading padding, and folds it after `seconds` (= `ocbar.bubbleSeconds`). The mark is a rule and not a wash: the row's hover wash *is* the pointer's own affordance (a mark would read as hovered from elsewhere), and tinting the ground would raise an all-alpha row's every tone.

**The pid is held** and re-applied on every `update`, because the alert arrives *before* the rows that contain it (the transition precedes the render tick that supplies them), so the mark lands on the row it means. A nil pid, or one absent from the tick's list, leaves the card on the whole ranked list and marks nothing (below). `name` is the session's folder display name, the key the retract matches on.

**While it is armed the card lists only the row it is about.** The alerted row *is* the list and every other session folds into the inert `+k more` footnote, whose count is therefore `ranked.count − 1`: an unprompted card exists because *one* session moved, so the full attention-ranked list would make the user hunt for the row that did — the alert would open a card and then make its own point the fourth row down. The scope lives inside `recomputeFold` (`alertArmed` + `alert.pid` are its inputs), not in a second list beside it, so the card, the window frame and the summary text still come off the one split, and the scoped row passes the same `IslandListBudget` as any other (a list of one always fits, so it is never the one that folds). `refoldCard()` is the one place a fold becomes a card (`recomputeFold` → signature → `rebuildRows` when it changed, reporting the change so an open card can be resized top-anchored); `update` runs it each tick, and so do `alert()` and `clearAlert()` — the alert's two ends — because they flip the scope without necessarily being followed by a tick that carries the rows: an alert can land on a card the pointer already had open, and its own timer ends it with no tick in sight. **The full list comes back in `clearAlert()`**, in the same frame the mark leaves; holding the scoped list until the card folded is not expressible, because `alertArmed` is this calculation's input and the next 0.5s tick would restore the whole list anyway — a hold would need a flag duplicating a fold this file keeps as one source. (`collapse()` folds *first*, so there the restore is invisible: `resizeOpenCard` is guarded on `expandedState`.)

**A card that opened must never open empty.** When the alert cannot be pinned to a row — a nil pid (bound to no running client), or a pid not in the tick's list because the session is filtered out or unbound — the card falls back to the **whole ranked list, exactly as a hover card shows it**, and marks nothing. An alert with nowhere to point is still a card the user has to be told about, and a card armed while the island is off screen lands here with no rows at all and scopes on the first tick that has the row.

**While an alert is armed the alert's own timer owns the fold** (`alertWork` — deliberately not `expandWork`/`collapseWork`, which `cancelPending` clears on every expansion): `scheduleCollapse` must refuse to *schedule* one at all (the 0.15s poll would otherwise fold the card ~0.35s after it opened), and `alert()` must also cancel a fold **already booked**, which that guard alone cannot reach. Re-arming replaces the deadline rather than stacking, and re-arming on the *same* row still pops — its spring is keyed on a monotonic generation, so a poll tick cannot restart it. Reduce Motion takes only the pop, never the rule: the rule *is* the information. **An alert ends in exactly one place, `clearAlert()`**: its own timer, `collapse()` (the menubar, a row click, or the `Hide` button — all the user answering), and `hide()` (no rows, or a retired display).

**The hold is `bubbleSeconds`, but it can be cut short when the user is already looking at the terminal.** With `ocbar.alertFocusedFold` on (**off by default**), `AppDelegate.shortenAlertIfTerminalFocused` asks two questions: is the app hosting the session's tty `NSWorkspace.frontmostApplication`, and — for a tmux pane — is that pane the one its session is **showing**? The second is `SessionMonitor.terminalHostAppPID(forClient:)`'s gate (`pane_active` + `window_active` + `session_attached`, plus the ppid walk and the one tmux hop a pane's *daemonized* server otherwise hides: a pane's shell is a child of the server, whose ppid is 1, so the terminal is reached through the tmux client's tty instead). **The pane half is load-bearing, not a refinement**: every pane shares the app, so "the app is in front" alone read a session sitting in a background tmux window as seen and folded its card early. When both hold, the panel's deadline is pulled in to `alertFocusedSeconds` (2s). `IslandPanel.shortenAlert(to:)` is the only way in and **touches nothing but the deadline**: not `alert`, not `alertGeneration` (the row's pop is keyed on the generation, and a shorter hold is not new information that deserves a second pop), not the fold (the same one row is listed either way). **`alertDeadline` is why the deadline is stored beside the work item** instead of being baked into it: an activation fires more than once — bring the terminal forward, click in it, come back — and a naive re-arm would push the fold `alertFocusedSeconds` out on every one, so a request that lands *later* than the armed deadline is ignored. The host is remembered (`alertHostAppPID`, cleared on every arm and on `dismissReminders`) so an alert that fired in the **background** is cut the moment that app is activated (`terminalActivated(_:)`): bringing an app forward *is* the event, so nothing polls for it. **It is not a fourth exit** — only the timer's deadline moves, and the alert still ends in `clearAlert()` alone. Two approximations remain, and they are why the setting ships off: the **tab across different tmux sessions** (a terminal with two tabs attached to different sessions cannot say which is in front — a terminal's focused surface is invisible from outside without Accessibility, never requested here, or a per-terminal AppleScript, and Ghostty 1.3 dropped the `tty` property `focusCommand` was written against), and a non-tmux client, where no pane question can be asked and the app is all there is to report. The bubble is untouched either way — it has its own click-to-focus.

**Three exits, and exactly two of them latch.** (1) The card's only button, `Hide` (`IslandCardButton`): 11pt regular (the age/context/`+k more` size) at white α0.55 → α0.7 on hover, over a resting ground of **half the card's own hover wash** (α0.045 = `islandHoverWashAlpha / 2`) returning to the wash (α0.09, the row's own fill, inset 3/2, radius 7) in 0.15s — half a hovered row, never brighter. Its **action row exists only while an alert is armed** (a hover-opened card needs no way out: leaving already folds it) and is the card's short-row height `summaryRowHeight` (24), so it is chrome in `IslandListBudget` like the folded row ([`island.md`](island.md)); it is its own `hitTest` target (`acceptsFirstMouse`, press swallowed, release-inside activates), and its one action is the shared dismissal **without** `focusSession`. (2) A row click — the same dismissal *plus* focus, wired host-side in [`island.md`](island.md). Both go through `collapse()`: in both the pointer is inside the island by construction, and the latch is what stops the poll re-opening what the user just closed. **`IslandPanel.collapse()` latches the hover open off until the pointer leaves** (`hoverLatched`), without which the next 0.15s tick re-expands the card 0.35s later; released only by the pointer being *seen* outside the hover rect, or by anything else opening the card (an alert is new information, not the poll second-guessing a dismissal); `hide` and `present` clear it. The hover poll is a `.default`-mode timer AppKit does not service during menu tracking, and must not become `.common`. (3) The **retract**, which deliberately does *not* latch: `SessionMonitor.onDismiss` → `AppDelegate.dismissReminders` (beside `bubble.dismiss`, same folder display name) → `IslandHost.dismissAlert(named:)` → per-panel `retractAlert(named:)`, firing only where the armed alert's name matches, and ending it as the *timer* does (`endAlert` = `clearAlert()` + `evaluateHover`): the card goes back to the hover machine, so an unattended card folds on the ordinary deadline while one being pointed at stays up. The pointer can be anywhere here, which is why this exit must not latch: merging it into `collapse()` loses a behaviour either way.

**A blank click is not an exit, and `onClick` is where that is enforced.** `IslandCardView.hitTest` hands the remainder of the card — its margins, and the inert `+k more` footnote, which falls through by design — to the card's `onClick`, which toggles the island ([`island.md`](island.md)). On a hover card that is the way out; **while an alert is armed `onClick` refuses the fold** (`alertArmed && expandedState`), so a stray click on the card does nothing at all. Without the refusal that click was neither exit (1) nor (2): `setExpanded(false)` latches nothing and does not call `clearAlert()`, so the reminder stayed armed but unseen — and if the pointer happened to remain inside the collapsed hover rect, the 0.15s poll popped the card back 0.35s later. One click, two outcomes, on the one surface whose whole job is to be noticed. Clicking a *collapsed* card still opens it: with an alert armed, `collapse()` is the only fold, and it ends the alert.
