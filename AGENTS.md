# AGENTS.md

macOS menubar app (Swift/AppKit, no SwiftUI) that monitors OpenCode sessions across terminals. App code lives in `ocbar/`.

## Build & run
- **Canonical build is `build.sh` at the repo root, not Xcode.** From the repo root:
  ```bash
  ./build.sh                            # swiftc compile -> ocbar/ocbar_bin, bundles ocbar/ocbar.app
  ./build.sh && open ocbar/ocbar.app    # rebuild + launch after code changes
  ```
- Requires Xcode Command Line Tools (`xcode-select --install`). Builds **arm64-only**, target `macos13.0`.
- App is `LSUIElement` (menubar-only, no Dock icon). Notifications permission prompt appears on first run.
- If macOS blocks the app: System Settings → Privacy & Security → Open Anyway.
- Project copy is `ocbar/ocbar.app`; if you also copied to `/Applications`, `cp -R ocbar.app /Applications` again after each rebuild.
- `ocbar_bin` and `ocbar.app` are gitignored build artifacts.

## Adding / editing Swift files
- `build.sh` compiles an **explicit hardcoded file list** in order. A new `.swift` file is silently not compiled until added there (and to `ocbar.xcodeproj/project.pbxproj` to keep Xcode builds working).
- Top-level executable code is only allowed in `main.swift` (Swift rule) — keep it last in the list.
- No tests, no CI, no linter. Verify with a successful `./build.sh`.

## Architecture
- `main.swift` → `AppDelegate` (status item, menu, bubble, UserDefaults config) → `SessionMonitor` (`@MainActor`, owns 2s scan + 0.5s poll timers and `AppState`) → inline HTTP.
- Discovery: reads `~/.local/state/opencode/service.json` (url, pid, version, password) to locate the single shared OpenCode v2 service; authenticates with HTTP Basic auth (username `opencode`, password from that file). `ProcessScanner.swift` is deleted.
- HTTP polling hits the service endpoints: `GET /api/info` (health/identity), `GET /api/session/active` (busy sessions), `GET /api/session?limit=100&order=desc` (session list incl. project directory), and `GET /api/form` / `GET /api/permission/request` scoped by `location[directory]=<dir>` (pending user input).
- Visibility: the 2s scan matches running processes by executable name (`ps -Ao pid=,comm=`, last path component `opencode`, excluding the `service.json` pid) and parses their argv. A session is shown only if a running client is bound to it by exact session id, so client-less orphaned sessions (e.g. blocked on a permission prompt) are ignored.
- A client pid is bound to **exactly** the session it is driving. The primary source is the **live binding published by the ocbar-bridge TUI plugin** (`~/.local/state/ocbar/bindings/<pid>.json`, see below); if a live client pid has no fresh binding file, ocbar falls back to parsing that client's argv (`ps -Ao pid=,args= -ww`, accepting `--session <id>` / `-s <id>` / `--session=<id>` / `-s=<id>`, i.e. a client started with `opencode --session <id>`). Either way the binding is exact pid↔session — there is no directory-level fallback. Sessions are not collapsed per directory — every bound root session is emitted individually.
- **argv alone is only a launch-time snapshot — the bridge plugin is what makes it live.** The v2 TUI can change which session it drives without touching its argv: `/clear`, `/new`, `/sessions` (aliases `/resume`, `/continue`), `ctrl+o`, `<leader>l`, `<leader>1..9` and session tabs all just `route.navigate` inside the process, so argv keeps naming the session the client was launched with. The ocbar-bridge plugin runs inside that same process and republishes the live route every 200ms, so these in-TUI switches now update the binding in real time — in particular a `/clear` followed by a message (which creates a brand-new session B in the same directory) binds to B correctly. (Historical symptom, still reachable only when the plugin is missing/stale: ocbar binds that pid to the stale launch session and drops the session actually being driven at the `guard let pid = sessionIDToPID[id]` check, so the only fix is relaunching the client with an explicit id.)
- **ocbar-bridge TUI plugin** — source `plugin/ocbar-bridge/tui.js`; `build.sh` installs it to `~/.config/opencode/plugins/ocbar-bridge/tui.js`. It runs inside the TUI client process, so `process.pid` there is the terminal client pid. Every 200ms it reads the live route (`ctx.ui.router.current()`) and atomically writes `{version, pid, sessionID, isRoot, directory, updatedAt}` to `~/.local/state/ocbar/bindings/<pid>.json` (temp file + rename, so ocbar never reads a half-written file); on teardown it deletes that file. ocbar's read priority for each live client pid: a fresh binding file (&lt;15s old) wins, and `sessionID: null` in it means the client is not in any session (e.g. parked on the home page after `/clear`) and ocbar does **not** fall back to argv in that case; only a pid with no fresh binding file falls back to argv parsing. Zero dependencies (only `node:fs`/`node:os`); `setup()` uses `setInterval` + a returned cleanup fn (it runs outside a Solid owner).
- The shell helpers that pass an explicit id live in `~/dev/git/stuff/workspace.sh`: `oc [args…]` mints a fresh random `ses_…` id and runs `opencode --session "$sid"`; `occ` runs `opencode --session <newest session id>` (falling back to `opencode --continue`); `oct` creates `~/ocsession/<yyMMdd-HHmmss>-<rand>/`, `cd`s into it and launches a fresh random id there. A bare `opencode` (no `--session`) carries no id in argv, so without the plugin it is never bound (with the plugin it binds once it enters a session). **Since the bridge plugin binds by live route, the id these helpers pass is no longer needed for ocbar visibility** — passing `--session <id>` still matters only when an id must be chosen *before* the session exists (pre-assigning an id for another consumer) or to jump straight to a specific existing id non-interactively; a bare `opencode` binds the same way once it enters a session, and the TUI's `/sessions` covers resuming interactively. These helpers are the maintainer's **personal** shell functions — nothing ships them — so keep them out of README: other readers don't have them. README should only ever say `opencode --session <id>`.
- Note on the plumbing: OpenCode v2.1.0's **server** exposes **no** client↔session mapping (no client registry, no presence/attach endpoint, `/environment` and `/inbox` are empty; `session.viewed` is only an idle-ack watermark), so the pid↔session link has to come from the **client side**. That client-side publisher now exists — it is the ocbar-bridge plugin above, which reports each client's live session from inside its process; argv parsing is kept only as the fallback for clients without the plugin. The alternatives (accepting client-less busy sessions, or rebinding a pid by directory) were both tried and removed earlier for producing stale sibling rows; see git `ff2dea0`.
- **`OpenCodeClient.swift` is currently dead code** — nothing references it; `SessionMonitor` inlines its own HTTP calls. Don't extend it expecting it to be wired in.
- **Context-window usage** (off by default; shown on the dropdown's detail row and, when on, as the island row's third line) is filled by `SessionMonitor.fillContext` and carried as `SessionInfo.context` (`SessionContext{used, limit, fraction}`, `Models.swift`); it is gated on `UserDefaults` keys `ocbar.contextUsage` (master, default false), `ocbar.contextUsageDisplay` (`percent`|`tokens`|`both`, default `both`), `ocbar.contextUsageWarn` (default 80) and `ocbar.contextUsageCritical` (default 95), all menu-driven in `contextUsageMenu()`. When on: the ceiling comes from `GET /api/model` (`limit.input`/`limit.context`/`limit.output`, TTL-cached 300s) through a copy of opencode's own `usable()` rule (`packages/opencode/src/session/overflow.ts`: `mx = min(output ?? 32000, 32000)`, `usable = input ? input - min(20000, mx) : context - mx`; 46/110 models have no `limit.input`), and the usage from `GET /api/session/<id>/message?limit=10`, taking the first entry with `type == "assistant"` **and** a `tokens` object, because the list is newest-first and the in-flight turn carries no `tokens`. `used = input + output + cache.read + cache.write` — `reasoning` is deliberately excluded and `input` excludes cache, so the prompt is `input + cache.read + cache.write`. `Session.Info.tokens` in the session list is **cumulative** and must not be used for this. Per-session refresh is throttled to 2s. The dropdown row is an indented, non-actionable item whose leading badge image is the session row's own glyph width (`contextDetailItem(for:)`), which is what aligns its text under the session name; `contextDetailExtraInset` is the tuning knob.
- **`IslandPanel.swift`** — the "灵动岛"/notch island, a third surface alongside the menubar item and the bubble. A borderless, non-activating `NSPanel` at `NSWindow.Level(mainMenuWindow + 2)` (above the menu bar), top-anchored, and **one panel per attached screen**: `IslandHost` keeps one `IslandPanel` per `NSScreen.screens`, rebuilding the set on `didChangeScreenParametersNotification` (geometry is re-measured on every use, so only a change to the *set* of displays rebuilds, and a removed display's panel is retired). Each panel keeps its own hover poll, expansion and fold, so showing on every screen costs one layer-26 window plus one 0.15s poll per screen. On a screen that has a notch it is anchored to the cutout rather than to screen centre — the collapsed capsule spans `cutoutLeft − 130 … cutoutRight + 130`, and the expanded card is centred on the cutout (`NSScreen.auxiliaryTopLeftArea`/`auxiliaryTopRightArea` for the width, `safeAreaInsets.top` for the height). On a display with no cutout it becomes a top-centred stand-in capsule `islandStandInCapsuleWidth(screenWidth:)` wide — a share of the screen (`min(max(screenWidth × 0.14, 160), 240)`) **floored by what that capsule has to hold** (`CollapsedContentView.standInCapsuleMinWidth`, **172pt**: the ring + the right flank's three two-digit badges + the running slot's bare two-digit count + the gaps + clearance — 19pt narrower than the 191 it was while that slot still carried a glyph) — and the card centres on the screen so it stays concentric with it. That second floor is load-bearing and was a real defect: the share alone asks for 143pt on a 1024-wide display and clamps up to the 160 floor, which is *narrower* than the 184.3pt block, so `place` would collapse every badge-to-badge gap to zero (measured: −0.06) and pin the block to the capsule's edge with the mask trimming the rest. The floor is only ever a floor, never a replacement for the fraction: on the maintainer's 1512pt display the share still sets the width (211.7), and the 240 cap still holds on large ones. Collapsed it is a black capsule whose two flanks are **the same width** — 130pt each, so a 445pt capsule for a 185pt cutout, with the cutout at its centre. Symmetry, not either side's content, is what sets that width: `islandFlank` is `CollapsedContentView.flankWidth` = `max(requiredLeftFlankWidth, requiredRightFlankWidth)`, used for **both** sides, so the capsule is symmetric about the notch by construction and the two regions `layout()` fills are equal without any further arithmetic. The two needs are derived from the metrics of what each side holds: the right is the measured least width that fits **three two-digit badges** (the states left after the running one moved: error, waiting, idle) + two `groupGap`s + clearance = 130pt; the left is the ring (12pt) + `groupGap` (6) + **that slot's two-digit count** (18.57) + clearance = 43pt. The right's is the wider one, so it still sets `flankWidth` and the left wing carries 130 − 36.57 = 93.4pt of empty room as the price of a balanced capsule — the capsule is 445pt before and after the arrow's removal, and the side that binds did not change. The rejected alternative is symmetry at the *smaller* width: provision the right flank for **one**-digit counts and both wings become 108 (pill 401), which saves 44pt — and `place` then trims a two-digit count at the capsule edge *silently*, so a fourteen-session finished count would be drawn as `1`. A wrong number is worse than 44pt of black, and this pill has been built to avoid exactly that failure. It is launch geometry — the window's x is computed from it — and a strict upper bound for both sides. Every extra point sits over the menubar strip either side of the cutout, so this is the minimum that makes two-digit counts readable, not slack: the pill is 445pt, 68pt wider than the 377pt it was when each wing was sized to its own contents, and **all of that growth is leftwards**: the trailing edge stays at x 980, so the outer 532pt of menubar — where the status items live — is untouched, while the leading edge reaches from 603 out to x 535, 68pt deeper into the menu-title strip. A symmetric capsule around an off-centre notch has to pay for itself somewhere, and this is where it pays. Provisioning the right flank for two digits rather than one is deliberate: a count is a fact, and a too-narrow flank fails *silently* — `place` trims the overflow at the capsule edge, so a twelve-session idle count would be drawn as `1`. Sizing a count by `intrinsicContentSize` is **not** enough and was a real bug: that is the bare glyph advance (7.5pt at 2×, 8.0 at 1×), while the cell lays the digit out ~2.9pt in and clips at the frame edge, so the widest-ink digits were shaved by ~1pt on the right — visibly only on `2`/`0`/`3`–`9`, never on `1`, which is why the pill looked as if only its busy count was cut. `islandLabelWidth(for:)` is therefore the **only** way an island label's width may be derived from its own text — `max(intrinsicContentSize, cell.cellSize(forBounds:))` (11.3pt for one digit, ~2.9pt more than the advance) — and `IslandMarkerGroup.flankWidth(atHeight:)`, the marker number's frame, `twoDigitCountWidth` and the row's right-aligned age all call it, so the digit and the age cannot drift apart. The age was a second instance of the same shave (`5h36m` needs 0.78pt more than its advance, and its frame ends 10pt from the card edge, so the cut is inside the label's own cell). Labels the layout sizes instead — the row's name, title and context — are immune and were measured so: the cell truncates *inside* its drawing rect, leaving the ink 43/213/116pt short of the frame edge, so their ellipsis can never be shaved; `cellSize` is also backing-scale independent, so both pills lay out identically) carrying **two different jobs, one per side**. Left: a status light that is **never hidden** — a hollow ring (`IslandActivityView`), 12pt across on a 32pt pill, orange and turning while any session is running and the *same ring* dim neutral (`restingTint`, white α0.40) and still when none is — **followed by the number of sessions working, drawn bare**: no glyph, because the ring *is* this slot's glyph. (It used to be followed by a running badge — `⟳` orange + the count — and the arrow was redundant: a filled disc with a knocked-out arrow is the same construction as every other state's glyph, so the flank showed two orange shapes side by side, one of them turning, both saying "running"; the ring's tint *and* motion already carry that, so the slot keeps only the count. The counts themselves are white everywhere: orange belongs to glyphs, and this slot has none.) The ring measures **12pt** and the glyphs are 11pt SF Symbols whose ink **measures 12.00 × 12.00pt** inside their 14pt image box (`widestGlyphWidth`), the cap is **12pt** and the glyphs are 11pt SF Symbols whose ink **measures 12.00 × 12.00pt** inside their 14pt image box (`widestGlyphWidth`), read off the pill's own render at 1×, 2× and 8×. The harness asserts the two boxes agree to 0.3pt from one render (`silhouetteMatch`), and the measure has to be the silhouette's **extent** — any pixel the shape reaches into: a filled symbol's outermost sliver is a low-coverage skirt that a *strict* cut-off (>25%) trims, reporting 11.0–11.25, while a stroked ring's harder edge still reports 12.00. That is rim *density*, not size. An earlier note in the file read the strict number as the size and claimed the ring was "0.75pt larger as drawn" — wrong, and corrected. A 14pt cap (the one before) matched the glyphs' *box* instead, by putting the ring's centre-line on their ink; the maintainer's eye said the two silhouettes should match, and 12 is the size that does it. Its ink is 63pt² against the filled glyph's ~99pt² disc, the right hierarchy for the one mark on the pill with no number — attention comes from hue and motion. The caps this replaced were 24pt (75% of the pill's height, 218pt², 2.1× a glyph: it read as the pill's headline while being its least informative element) and then 14pt; every size was chosen off a ramp rendered from this code, now at 11/12/13/14pt, and the harness measures the two ink boxes against each other in points (`silhouetteMatch`). The stroke is `max(2.0, 0.14 × diameter)`, so the shipped size is on the floor and a smaller ring can never come out thinner than the digits beside it (an 11pt semibold digit's stems are ~1.7pt). It is always drawn because it used to exist only while something ran, which left the left flank a blank stub of black beside the right wing whenever nothing was — a blank wing beside a full one reads as something missing rather than as a state. Two channels carry "running" and either alone suffices: **tint** (orange vs dim neutral) and **motion** (turning vs held). That redundancy is required, not decorative: Reduce Motion deletes the motion, so the tint has to carry the state by itself — under it a running pill is a bright orange still ring and a quiet one a dim grey still ring (measured mean ink 0.88/0.50/0.16 lum 0.56 vs 0.38/0.38/0.38 lum 0.38), which motion alone could never give. Only `counts[.busy] > 0` can change the tint: it does not chase the per-state colours (an errored or waiting session is the badges' business, and tracking them would make the wing flicker between tints), and it stays orange while *any* session is busy, so other sessions coming and going do not blink it. The mark's *size* does not change with state, so the left flank is 130pt either way and a running/not-running transition moves nothing — the window x is untouched. And the ring does not *move* either, which is why the left flank is laid out **pinned** (`FlankAlignment.pinned(inset:)`) at `CollapsedContentView.leftContentInset` — the offset that centres the ring + running-badge pair in the 130pt wing, 47pt on the built-in display — while the right is centred. Three candidates were rendered and measured, all keeping the ring still: pinning at the outer edge (ring x 4) leaves 71pt of black between the count and the cutout; pinning at `leftContentInset` (x **47**, **shipped**) puts the pair at 47…83.6, i.e. centred in its wing; the value follows `leftContentWidth`, so dropping the arrow moved the ring 37 → 47 in one step and it sits at 47 in **both** states (measured off the renders: ring ink x 47…58 running and quiet, against 37…48 before); centring the *actual* content moves the ring 18pt on every busy↔idle transition (59 quiet → 41 running) and is rejected. Pinning at the ring-centred x instead (x 59) would centre the quiet state but push the pair to 59…114, 16pt from the cutout, i.e. off-centre in the state you actually look at. That is the one place the two flanks use different alignments, and the reason is that only the left has an always-present element whose position is a landmark. **It is the app's one running mark, not just the pill's** (maintainer's decision, 2026-10: the menubar's wedge spinner and the card row's static orange `arrow.clockwise.circle.fill` were both deleted in favour of it). All of its geometry and both its tints live in `IslandRing`, and its shape is built once, in `IslandRing.arcPath` — which the live view strokes **and** `IslandRing.image(pointSize:angle:)` renders into an `NSImage`, because the menubar title (a text attachment) and the dropdown rows (menu-item images) cannot host a view. Four surfaces, one mark: the pill's left flank (12pt, `diameterCap`), the card rows (`IslandRowView.ringDiameter` — the check-circle's **ink** measured at the row's own 13pt semibold and fitted into the row's 15pt glyph box: 13.125pt, so a running row is the same size as the idle/waiting/error rows beside it), the menubar title (12.000pt, measured from the same circle at 11pt) and the dropdown rows (14.000pt at 13pt), the last two keeping the old spinner's **canvas contract** — the image box, which the title attachment's bounds/baseline nudge and the dropdown's detail-row alignment are computed against. Also: every live mark on the island subscribes to `IslandRingTicker`, the island's **one** 0.06s tick source, so a card holding four busy rows plus the pill costs one timer rather than five (the menubar keeps its own, because its tick drives `NSImage` swaps `AppDelegate` owns and it runs whenever anything is busy rather than only while a window is up; only its *phase* is shared, through `angle(at:)`). What it is deliberately not is any *other* shape in its neighbourhood: a filled disc is still what every badge glyph on the pill is (`…circle.fill`), so a filled disc on the flank would be an oversized copy of the orange badge beside it — a badge that lost its number — and is also what the menubar's old mark was. It is what was *given up* that is worth recording: the ring is hollow and its ink is lighter than the solid discs it now sits among in the menubar title and the dropdown, and the menubar title is the smallest showing there is (11pt, an 11pt title line), so the busy entry there is a quieter mark than the solid orange disc it replaced. A pixel-art mascot was rejected for the same reason the 8pt dot failed: a second drawing technique beside SF Symbols. The gap stays 90° at every size — what has to stay legible is the gap *in stroke widths* and the round caps scale with the stroke: measured on the rendered ring, the opening is **3.0 stroke widths at the shipped 12pt**, 2.5 at 11pt, 3.4 at 13pt and 3.7 at 14pt. 3.0 is the floor at which a gap still reads as an opening, 12 is the exact match, which is why it ships; 11 would be 1pt under and its gap tighter. 11pt would be 1pt *under* the glyph and its gap falls to 2.5 stroke widths, so there is no trade left to make at 12. **Motion is 18° per 0.06s tick (300°/s, one revolution in 1.2s, clockwise) everywhere** — the menubar and dropdown included. The 45°/tick (750°/s) that the menubar's mark used to run at existed for its *shape*, not for the menubar: a filled disc with a 70° wedge knocked out has a low-contrast moving part, so 300°/s barely registered on it, whereas the ring's 90° gap is a large high-contrast discontinuity that at 750°/s would lap the ring every 0.48s and read as a warning blink. `IslandRing.angle(at:)` is a pure function of the clock, so every ring in the app is at the same angle at the same instant instead of holding four phases, and a late tick cannot drift one away from the others. Three gates on the island's views, all in `IslandActivityView.shouldPlay`: something running; `!NSWorkspace.shared.accessibilityDisplayShouldReduceMotion` (under which the ring is shown but held at `restingAngle`, gap centred on 12 o'clock so a still mark reads as deliberate rather than stalled, and the setting is re-read on `NSWorkspace.accessibilityDisplayOptionsDidChangeNotification` — **the menubar's and dropdown's marks honour it the same way now, for the first time in this app**, and `updateRunningMark` *stops its 0.06s timer* rather than repainting a still image, restarting it on the same notification); and `onScreen`, which `IslandPanel.present()`/`hide()` set for the pill and `IslandPanel.rowsOnScreen` (`visible && expandedState`) adds for a card row — because those are the only two places the panel is ordered in or out, and a row behind the collapsed pill is not something to turn a ring for. The timer is created in `updateMotion` when the mark starts playing and invalidated the moment it stops — **there is no timer while nothing is running**, the mark is simply drawn still, so a quiet pill costs nothing — and `tick()` re-checks the same gate so the two cannot drift. Right: the tally — **one badge per remaining state that has sessions**, most urgent first, which is `CollapsedContentView.rightBadgeOrder` = `[.error, .waiting, .idle]`: `attentionRanked`'s ranking minus the running state, which now has its own slot on the left as `CollapsedContentView.runningStatus`. So the pill's reading is two questions, not one urgency list — "is work happening + how much" (the ring and its count, left), then "what needs me, most urgent first" (right) — and the right flank's order is still exactly the order the card sorts its rows by. `badgeStatuses` (`[runningStatus] + rightBadgeOrder`) is the one place all four states are listed, so a state cannot be forgotten by one flank while the other draws it. Three of those slots are a tinted status glyph plus the number of sessions in that state, all through the identical construction (`CollapsedContentView.show(_:count:in:)` → `IslandMarkerGroup.badgeImage`, one point size, one gap, tabular digits); the fourth — the running one — is the count **alone**, which is why `symbol(for:)` returns `nil` for `.busy` and why `IslandMarkerGroup` decides the glyph's and the count's visibility separately (a zero count is what makes a badge not exist). **Nothing is ever dropped**: the four states have four slots, so `maxAttentionGroups` and the whole drop-the-least-urgent rule are gone, and the pill can no longer hide an error while a less urgent state stays on show — which is exactly what the previous two-slot cap did (it drew `! n ? m` and dropped the finished count). The pill's input is one dictionary, `CollapsedContentView.counts`; the counts and the status light are both derived from it, so the mark is orange and turning exactly while the running count is showing and the two cannot disagree. The ring is the pill's pulse (something is happening now) and the number beside it is its tally (how many) — and only the ring is orange: the number is white like every other count on the pill, because colour on this surface lives on glyphs. Content is never anchored to the cutout or the capsule edge. The **right** flank is *centred*, so a flank provisioned for three badges but holding one does not look lopsided; the cost is that a badge shifts ~18pt when a state appears there. The **left** flank is *pinned*, for the ring-landmark reason above. On a display with no cutout there is one region and one centred block, so the ring does shift there with the block — the notched case is the one the alignment decision is about. The empty pill is unreachable (`update` hides the island when there are no rows, and every row has one of the four states). This replaced two designs that failed in ways worth not repeating: a hand-drawn 8pt orange dot beside 11pt SF Symbols whose ink measures 12pt (the busiest state at 67% of its neighbours' size, sitting in the badge row where a badge was expected — drawn by separate code, which is precisely why nothing caught it), and then a glyph + count group per state capped at two, which dropped a state the pill knew about. The mark is not in the badge row at all now: other side of the cutout, the glyphs' own apparent size, no count, and a shape class no badge uses. On hover it grows into a rounded card **500pt** wide (`islandExpandedCardTargetWidth`, derived from the row's own fonts against the 200 most recent real session titles on the maintainer's machine; bounded to `0.8 × screen width` so a small display degrades instead of overflowing, floored at the collapsed capsule — now 445pt, so the floor itself binds below a ~556pt screen while the `0.8 × screen` bound binds below ~625 — and the card is only 1.12 × the pill where it used to be 1.33 ×. That ratio was never a target, only what two independent derivations produced, and the card is still sized by its *titles*: 500pt truncates none of the 200-title corpus, so widening it to restore a ratio would add black and no information, and narrowing it would cut titles to make a small pill look grander. The expansion reads through height, corner radius and alpha as well as width) listing each session as **up to three stacked lines — folder name + right-aligned age / title / context usage — never two fields on one line**, each absent line collapsing the row by exactly its own height. Row height is therefore `30 + 14 × (lines − 1)` (`islandRowHeight(lines:)`, one source of truth shared by the card layout, the height budget and the window frame), a full three-line row being 58pt. The context line is the menubar detail row's readout in white α0.5 (`12k / 200k tokens · 6%`, banded warn orange / critical red with the band glyph in the status-glyph column, placeholders at white α0.32). The list is **capped by a height budget, not a row count** (`IslandListBudget`: the smaller of 40% of the screen's usable height and the distance from the top edge to the bottom of the usable area, less chrome; each row contributes its own height), and the tail folds into an inert `+k more` row — inert because `IslandCardView.hitTest` hands clicks only to session rows and — while an alert is armed — to the `Hide` button in its own frame. Folding is safe only because the list is re-ranked `error < waiting < busy < idle` (stably, in `attentionRanked`) and the first row is always taken, so a fold can never hide an error while an idle row stays on show; and a row click goes to the host — `IslandHost.rowActivated` collapses **every** panel first (see the alert passage above) and then calls `onSelectSession(pid)` → `SessionMonitor.focusSession`. The island and the dropdown cannot drift on context usage: thresholds, wording, display mode and banding are resolved once in `Models.swift` (`ContextUsagePresentation`, `ContextBand`, `ContextDisplayMode`, `compactTokens`) and consumed by both the menu's `contextDetailItem` and `AppDelegate.islandContext` — the island only decides how to paint it on black. One latent trap fixed on the way: a non-positive `limit` is now treated as unknown rather than divided by, because the old inline maths reached `Int(Double(used)/0 * 100)` and trapped. Three non-obvious requirements, each of which was a real bug here: (1) **hover is polled**, a 0.15s `NSEvent.mouseLocation` check against the *target* rect — **not** `NSTrackingArea`, whose `.inVisibleRect` area is torn down and rebuilt by the window-resize animation, synthesising `mouseEntered`/`mouseExited` pairs while the pointer never moves (that made the island oscillate expand↔collapse forever); (2) the expand/collapse delays are **one-shot** and must be guarded (`expandWork == nil` / `collapseWork == nil`) — the poll re-runs every 0.15s, so a naive cancel-and-reschedule pushes the 0.35s deadline back on every tick and the island never expands or collapses at all; (3) the panel **must be keyable** (`canBecomeKey` true, `canBecomeMain` false) and every hit-testable view must return `acceptsFirstMouse == true` — a non-keyable non-activating panel belonging to an inactive accessory app receives no mouse events whatsoever, so with `canBecomeKey` false the pill click, the row click and the tmux jump are all silently dead while hover still works (hover only reads the cursor, it needs no events). Because it is a `.nonactivatingPanel`, becoming key does not activate the app or take the frontmost app's keyboard focus. `AppDelegate.render` pushes `[IslandRow]` to the `IslandHost` on every poll tick, which fans the one list out to every screen's panel — the push hops to the main actor (`Task { @MainActor in }`) because `render` is nonisolated while `IslandHost`/`IslandPanel` are `@MainActor`; `menuWillOpen` calls the host's `collapse()`, which collapses **all** of them; menu → "Show island" (`ocbar.island`, default on) toggles them, and with no rows (or disabled) every panel is ordered out. **The island is also a reminder surface, and this is its only *unprompted* expansion.** `IslandHost.alert(kind:pid:seconds:)` (`IslandAlertKind.waiting`/`.ready`) opens the card on **every** screen's panel, marks the transitioning session's row with a saturated 3pt rule in the row's leading padding, and folds it after `seconds` — which `AppDelegate.showBubble` passes as `ocbar.bubbleSeconds`, on the same two transitions the bubble uses, when the bubble is off and the island is on. The mark is a rule and not a wash because the row's hover wash *is* the pointer's own affordance (a marked row would read as hovered while the pointer is elsewhere, and a row that was both could not say which it was), and because a tinted ground under a row whose whole hierarchy is alpha raises all four tones together and double-encodes the status glyph beside it. The pid is **held** and re-applied on every `update`, because the alert always arrives *before* the rows that contain it — the transition comes from `SessionMonitor.publish`, the rows from the render tick after it — so the mark lands on the row it means rather than on that row as it looked one tick ago; a nil pid, or a session whose row folds into `+k more`, simply leaves no row marked. **While an alert is armed the alert's own timer owns the fold** (`alertWork`, deliberately not `expandWork`/`collapseWork`, which `cancelPending` clears on every expansion): `scheduleCollapse` refuses to *schedule* one at all — the 0.15s hover poll sees the pointer outside an expansion nobody asked for and would otherwise fold the card ~0.35s after it opened — and `alert()` additionally cancels any fold **already booked**, which that guard alone cannot reach. An alert therefore ends in exactly one place, `clearAlert()`, called by its own timer, by `collapse()` — the menubar opening, a row click, or the `Hide` button, all of which are the user answering — and by `hide()` (no rows, or a retired display). **A row click is answered by the host, not by the panel** (`IslandPanel.onRowActivated` → `IslandHost.rowActivated`): the reminder is on every screen, so one click folds *every* screen's island and only then hands the pid to `onSelectSession`, which still fires `focusSession` — folding just the clicked panel would leave the other display's card open for the rest of `bubbleSeconds`, still marking a row the user has already dealt with. That click and `menuWillOpen → collapse()` share one primitive, `IslandPanel.collapse()`, which **latches the hover open off until the pointer leaves** (`hoverLatched`): the pointer is inside the island the user just clicked — on a display with no cutout the rows start *above* the collapsed capsule's bottom edge, so the re-open is guaranteed rather than a race — and the next 0.15s poll tick would otherwise bring the card back 0.35s later. The latch is released only by the pointer being *seen* outside the hover rect, and by anything else opening the card (an alert is new information, not the poll second-guessing a dismissal); `hide` and `present` clear it too, so it cannot stick to an island that was off screen when it was set. (The menu path never suffered from this in practice — its pointer is at the status item, outside every island's rect, and the poll is a `.default`-mode timer AppKit does not service while a menu is tracking, so nothing re-expands under an open menu.) **The alert has three exits, and exactly two of them latch.** (1) The card's only button, `Hide`, every number in it from this card (`IslandCardButton`): the subordinate type (11pt regular — the age, context and `+k more` size) at white α0.55 → α0.7 on hover (the age's and the title's steps), over a resting ground of **half the card's own hover wash** (white α0.045 = `islandHoverWashAlpha / 2`) that returns to the wash itself on hover — same fill, same inset 3/2, same radius 7 a session row takes under the pointer — on the file's own 0.15s micro duration and (0.22, 1.0, 0.36, 1.0) curve. Measured off a 2× render of this code: card 2/255, resting button 13/255, a row under the pointer 25/255, hovered button 25/255 — so a resting button is half of a hovered row, never brighter, and the hover doubles the ground. It sits on an **action row that exists only while an alert is armed** (a hover-opened card needs no way out — leaving already folds it), whose height is the card's own short row `summaryRowHeight` (24), so it is chrome in `IslandListBudget` exactly as the `+k more` row is and a fold cannot push the button past the screen edge; it is its own `hitTest` target in `IslandCardView` (`acceptsFirstMouse`, press swallowed, release-inside activates) and its one action is the shared dismissal **without** `focusSession`. (2) A row click — the same dismissal *plus* focus. Both go through `collapse()`, because in both the pointer is inside the island by construction and the hover latch is what stops the poll re-opening what the user closed. (3) `SessionMonitor.onDismiss` → `AppDelegate.dismissReminders` (beside `bubble.dismiss`, same key: the folder's display name) → `IslandHost.dismissAlert(named:)` → per-panel `retractAlert(named:)`, which fires only for the panel whose armed alert matches the name and ends the alert as its *timer* does (`endAlert` → `clearAlert` + `evaluateHover`) — **no latch**: there the pointer can be anywhere, so an unattended card still folds on the ordinary 0.35s deadline while one the user is pointing at stays up. Merging that exit into `collapse()` loses a behaviour either way (a latch freezes a card being read; no latch lets the poll re-open a card just dismissed), which is why the two are documented against each other in both files. It ends by handing the card back to the hover machine (`endAlert` → `evaluateHover`) instead of folding it, so a pointer inside by then keeps it open and one outside folds it on the ordinary 0.35s deadline. Re-arming replaces the deadline rather than stacking, re-arming on the *same* row still pops again (the mark's spring is keyed on a monotonic generation, so a 0.5s poll tick can never restart it), and Reduce Motion takes only the pop, never the rule — the rule *is* the information.

App targets OpenCode v2 only: all sessions share one `opencode serve --service` process, so no per-terminal `--port` is needed. v1 users should use tag `oc_v1`. The bubble is gated on `UserDefaults` key `ocbar.bubble` (default true, menu → "Show bubble"); `bounceIcon()` rides with it, since the bounce only exists to point at the bubble. With the bubble off the **island** carries those same two moments instead (`island.alert`, see the `IslandPanel.swift` bullet above), so the reminder is a chain — the bubble, else the island, else nothing beyond `SessionMonitor`'s own system notification — and not two independent switches. The alert sound (`ocbar.alertSound`, default `off`) belongs to neither surface: it rings whenever one of them is about to show something.
