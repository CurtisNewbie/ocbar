# AGENTS.md

macOS menubar app (Swift/AppKit, no SwiftUI) that monitors OpenCode sessions across terminals. App code lives in `ocbar/`.

## Build & run
- **Canonical build is `build.sh` at the repo root, not Xcode.** From the repo root:
  ```bash
  ./build.sh                            # swiftc compile -> ocbar/ocbar_bin, bundles ocbar/ocbar.app
  ./build.sh && open ocbar/ocbar.app    # rebuild + launch after code changes
  ```
- Requires Xcode Command Line Tools (`xcode-select --install`). Builds **arm64-only**, target `macos13.0`.
- App is `LSUIElement` (menubar-only, no Dock icon). Notifications permission prompt appears on first run.
- If macOS blocks the app: System Settings → Privacy & Security → Open Anyway.
- Project copy is `ocbar/ocbar.app`; if you also copied to `/Applications`, `cp -R ocbar.app /Applications` again after each rebuild.
- `ocbar_bin` and `ocbar.app` are gitignored build artifacts.

## Adding / editing Swift files
- `build.sh` compiles an **explicit hardcoded file list** in order. A new `.swift` file is silently not compiled until added there (and to `ocbar.xcodeproj/project.pbxproj` to keep Xcode builds working).
- Top-level executable code is only allowed in `main.swift` (Swift rule) — keep it last in the list.
- No tests, no CI, no linter. Verify with a successful `./build.sh`.

## Architecture
- `main.swift` → `AppDelegate` (status item, menu, bubble, UserDefaults config) → `SessionMonitor` (`@MainActor`, owns 2s scan + 0.5s poll timers and `AppState`) → inline HTTP.
- Discovery: reads `~/.local/state/opencode/service.json` (url, pid, version, password) to locate the single shared OpenCode v2 service; authenticates with HTTP Basic auth (username `opencode`, password from that file). `ProcessScanner.swift` is deleted.
- HTTP polling hits the service endpoints: `GET /api/info` (health/identity), `GET /api/session/active` (busy sessions), `GET /api/session?limit=100&order=desc` (session list incl. project directory), and `GET /api/form` / `GET /api/permission/request` scoped by `location[directory]=<dir>` (pending user input).
- Visibility: the 2s scan matches running processes by executable name (`ps -Ao pid=,comm=`, last path component `opencode`, excluding the `service.json` pid) and parses their argv. A session is shown only if a running client is bound to it by exact session id, so client-less orphaned sessions (e.g. blocked on a permission prompt) are ignored.
- A client pid is bound to **exactly** the session it is driving. The primary source is the **live binding published by the ocbar-bridge TUI plugin** (`~/.local/state/ocbar/bindings/<pid>.json`, see below); if a live client pid has no fresh binding file, ocbar falls back to parsing that client's argv (`ps -Ao pid=,args= -ww`, accepting `--session <id>` / `-s <id>` / `--session=<id>` / `-s=<id>`, i.e. a client started with `opencode --session <id>`). Either way the binding is exact pid↔session — there is no directory-level fallback. Sessions are not collapsed per directory — every bound root session is emitted individually.
- **argv alone is only a launch-time snapshot — the bridge plugin is what makes it live.** The v2 TUI can change which session it drives without touching its argv: `/clear`, `/new`, `/sessions` (aliases `/resume`, `/continue`), `ctrl+o`, `<leader>l`, `<leader>1..9` and session tabs all just `route.navigate` inside the process, so argv keeps naming the session the client was launched with. The ocbar-bridge plugin runs inside that same process and republishes the live route every 200ms, so these in-TUI switches now update the binding in real time — in particular a `/clear` followed by a message (which creates a brand-new session B in the same directory) binds to B correctly. (Historical symptom, still reachable only when the plugin is missing/stale: ocbar binds that pid to the stale launch session and drops the session actually being driven at the `guard let pid = sessionIDToPID[id]` check, so the only fix is relaunching the client with an explicit id.)
- **ocbar-bridge TUI plugin** — source `plugin/ocbar-bridge/tui.js`; `build.sh` installs it to `~/.config/opencode/plugins/ocbar-bridge/tui.js`. It runs inside the TUI client process, so `process.pid` there is the terminal client pid. Every 200ms it reads the live route (`ctx.ui.router.current()`) and atomically writes `{version, pid, sessionID, isRoot, directory, updatedAt}` to `~/.local/state/ocbar/bindings/<pid>.json` (temp file + rename, so ocbar never reads a half-written file); on teardown it deletes that file. ocbar's read priority for each live client pid: a fresh binding file (&lt;15s old) wins, and `sessionID: null` in it means the client is not in any session (e.g. parked on the home page after `/clear`) and ocbar does **not** fall back to argv in that case; only a pid with no fresh binding file falls back to argv parsing. Zero dependencies (only `node:fs`/`node:os`); `setup()` uses `setInterval` + a returned cleanup fn (it runs outside a Solid owner).
- The shell helpers that pass an explicit id live in `~/dev/git/stuff/workspace.sh`: `oc [args…]` mints a fresh random `ses_…` id and runs `opencode --session "$sid"`; `occ` runs `opencode --session <newest session id>` (falling back to `opencode --continue`); `oct` creates `~/ocsession/<yyMMdd-HHmmss>-<rand>/`, `cd`s into it and launches a fresh random id there. A bare `opencode` (no `--session`) carries no id in argv, so without the plugin it is never bound (with the plugin it binds once it enters a session). **Since the bridge plugin binds by live route, the id these helpers pass is no longer needed for ocbar visibility** — passing `--session <id>` still matters only when an id must be chosen *before* the session exists (pre-assigning an id for another consumer) or to jump straight to a specific existing id non-interactively; a bare `opencode` binds the same way once it enters a session, and the TUI's `/sessions` covers resuming interactively. These helpers are the maintainer's **personal** shell functions — nothing ships them — so keep them out of README: other readers don't have them. README should only ever say `opencode --session <id>`.
- Note on the plumbing: OpenCode v2.1.0's **server** exposes **no** client↔session mapping (no client registry, no presence/attach endpoint, `/environment` and `/inbox` are empty; `session.viewed` is only an idle-ack watermark), so the pid↔session link has to come from the **client side**. That client-side publisher now exists — it is the ocbar-bridge plugin above, which reports each client's live session from inside its process; argv parsing is kept only as the fallback for clients without the plugin. The alternatives (accepting client-less busy sessions, or rebinding a pid by directory) were both tried and removed earlier for producing stale sibling rows; see git `ff2dea0`.
- **`OpenCodeClient.swift` is currently dead code** — nothing references it; `SessionMonitor` inlines its own HTTP calls. Don't extend it expecting it to be wired in.
- **Context-window usage** (off by default; shown on the dropdown's detail row and, when on, as the island row's third line) is filled by `SessionMonitor.fillContext` and carried as `SessionInfo.context` (`SessionContext{used, limit, fraction}`, `Models.swift`); it is gated on `UserDefaults` keys `ocbar.contextUsage` (master, default false), `ocbar.contextUsageDisplay` (`percent`|`tokens`|`both`, default `both`), `ocbar.contextUsageWarn` (default 80) and `ocbar.contextUsageCritical` (default 95), all menu-driven in `contextUsageMenu()`. When on: the ceiling comes from `GET /api/model` (`limit.input`/`limit.context`/`limit.output`, TTL-cached 300s) through a copy of opencode's own `usable()` rule (`packages/opencode/src/session/overflow.ts`: `mx = min(output ?? 32000, 32000)`, `usable = input ? input - min(20000, mx) : context - mx`; 46/110 models have no `limit.input`), and the usage from `GET /api/session/<id>/message?limit=10`, taking the first entry with `type == "assistant"` **and** a `tokens` object, because the list is newest-first and the in-flight turn carries no `tokens`. `used = input + output + cache.read + cache.write` — `reasoning` is deliberately excluded and `input` excludes cache, so the prompt is `input + cache.read + cache.write`. `Session.Info.tokens` in the session list is **cumulative** and must not be used for this. Per-session refresh is throttled to 2s. The dropdown row is an indented, non-actionable item whose leading badge image is the session row's own glyph width (`contextDetailItem(for:)`), which is what aligns its text under the session name; `contextDetailExtraInset` is the tuning knob.
- **`IslandPanel.swift`** — the "灵动岛"/notch island, a third surface alongside the menubar item and the bubble. A borderless, non-activating `NSPanel` at `NSWindow.Level(mainMenuWindow + 2)` (above the menu bar), top-anchored, and **one panel per attached screen**: `IslandHost` keeps one `IslandPanel` per `NSScreen.screens`, rebuilding the set on `didChangeScreenParametersNotification` (geometry is re-measured on every use, so only a change to the *set* of displays rebuilds, and a removed display's panel is retired). Each panel keeps its own hover poll, expansion and fold, so showing on every screen costs one layer-26 window plus one 0.15s poll per screen. On a screen that has a notch it is anchored to the cutout rather than to screen centre — the collapsed capsule spans `cutoutLeft − 130 … cutoutRight + 130`, and the expanded card is centred on the cutout (`NSScreen.auxiliaryTopLeftArea`/`auxiliaryTopRightArea` for the width, `safeAreaInsets.top` for the height). On a display with no cutout it becomes a top-centred stand-in capsule `islandStandInCapsuleWidth(screenWidth:)` wide — a share of the screen (`min(max(screenWidth × 0.14, 160), 240)`) **floored by what that capsule has to hold** (`CollapsedContentView.standInCapsuleMinWidth`, 191pt: the ring + four two-digit badges + the gaps + clearance) — and the card centres on the screen so it stays concentric with it. That second floor is load-bearing and was a real defect: the share alone asks for 143pt on a 1024-wide display and clamps up to the 160 floor, which is *narrower* than the 184.3pt block, so `place` would collapse every badge-to-badge gap to zero (measured: −0.06) and pin the block to the capsule's edge with the mask trimming the rest. The floor is only ever a floor, never a replacement for the fraction: on the maintainer's 1512pt display the share still sets the width (211.7), and the 240 cap still holds on large ones. Collapsed it is a black capsule whose two flanks are **the same width** — 130pt each, so a 445pt capsule for a 185pt cutout, with the cutout at its centre. Symmetry, not either side's content, is what sets that width: `islandFlank` is `CollapsedContentView.flankWidth` = `max(requiredLeftFlankWidth, requiredRightFlankWidth)`, used for **both** sides, so the capsule is symmetric about the notch by construction and the two regions `layout()` fills are equal without any further arithmetic. The two needs are derived from the metrics of what each side holds: the right is the measured least width that fits **three two-digit badges** (the states left after the running one moved: error, waiting, idle) + two `groupGap`s + clearance = 130pt; the left is the ring (12pt) + `groupGap` (6) + **one two-digit running badge** (37.06) + clearance = 62pt. The right's is the wider one, so the left wing carries 130 − 55 = 75pt of empty room as the price of a balanced capsule. The rejected alternative is symmetry at the *smaller* width: provision the right flank for **one**-digit counts and both wings become 108 (pill 401), which saves 44pt — and `place` then trims a two-digit count at the capsule edge *silently*, so a fourteen-session finished count would be drawn as `1`. A wrong number is worse than 44pt of black, and this pill has been built to avoid exactly that failure. It is launch geometry — the window's x is computed from it — and a strict upper bound for both sides. Every extra point sits over the menubar strip either side of the cutout, so this is the minimum that makes two-digit counts readable, not slack: the pill is 445pt, 68pt wider than the 377pt it was when each wing was sized to its own contents, and **all of that growth is leftwards**: the trailing edge stays at x 980, so the outer 532pt of menubar — where the status items live — is untouched, while the leading edge reaches from 603 out to x 535, 68pt deeper into the menu-title strip. A symmetric capsule around an off-centre notch has to pay for itself somewhere, and this is where it pays. Provisioning the right flank for two digits rather than one is deliberate: a count is a fact, and a too-narrow flank fails *silently* — `place` trims the overflow at the capsule edge, so a twelve-session idle count would be drawn as `1`. Sizing a count by `intrinsicContentSize` is **not** enough and was a real bug: that is the bare glyph advance (7.5pt at 2×, 8.0 at 1×), while the cell lays the digit out ~2.9pt in and clips at the frame edge, so the widest-ink digits were shaved by ~1pt on the right — visibly only on `2`/`0`/`3`–`9`, never on `1`, which is why the pill looked as if only its busy count was cut. `islandLabelWidth(for:)` is therefore the **only** way an island label's width may be derived from its own text — `max(intrinsicContentSize, cell.cellSize(forBounds:))` (11.3pt for one digit, ~2.9pt more than the advance) — and `IslandMarkerGroup.flankWidth(atHeight:)`, the marker number's frame, `twoDigitCountWidth` and the row's right-aligned age all call it, so the digit and the age cannot drift apart. The age was a second instance of the same shave (`5h36m` needs 0.78pt more than its advance, and its frame ends 10pt from the card edge, so the cut is inside the label's own cell). Labels the layout sizes instead — the row's name, title and context — are immune and were measured so: the cell truncates *inside* its drawing rect, leaving the ink 43/213/116pt short of the frame edge, so their ellipsis can never be shaved; `cellSize` is also backing-scale independent, so both pills lay out identically) carrying **two different jobs, one per side**. Left: a status light that is **never hidden** — a hollow ring (`IslandActivityView`), 12pt across on a 32pt pill, orange and turning while any session is running and the *same ring* dim neutral (`restingTint`, white α0.40) and still when none is — **followed by the running badge**, `⟳` orange + the number of sessions working. Its size is **exactly** the badge glyph beside it: the cap is **12pt** and the glyphs are 11pt SF Symbols whose ink **measures 12.00 × 12.00pt** inside their 14pt image box (`widestGlyphWidth`), read off the pill's own render at 1×, 2× and 8×. The harness asserts the two boxes agree to 0.3pt from one render (`silhouetteMatch`), and the measure has to be the silhouette's **extent** — any pixel the shape reaches into: a filled symbol's outermost sliver is a low-coverage skirt that a *strict* cut-off (>25%) trims, reporting 11.0–11.25, while a stroked ring's harder edge still reports 12.00. That is rim *density*, not size. An earlier note in the file read the strict number as the size and claimed the ring was "0.75pt larger as drawn" — wrong, and corrected. A 14pt cap (the one before) matched the glyphs' *box* instead, by putting the ring's centre-line on their ink; the maintainer's eye said the two silhouettes should match, and 12 is the size that does it. Its ink is 63pt² against the filled glyph's ~99pt² disc, the right hierarchy for the one mark on the pill with no number — attention comes from hue and motion. The caps this replaced were 24pt (75% of the pill's height, 218pt², 2.1× a glyph: it read as the pill's headline while being its least informative element) and then 14pt; every size was chosen off a ramp rendered from this code, now at 11/12/13/14pt, and the harness measures the two ink boxes against each other in points (`silhouetteMatch`). The stroke is `max(2.0, 0.14 × diameter)`, so the shipped size is on the floor and a smaller ring can never come out thinner than the digits beside it (an 11pt semibold digit's stems are ~1.7pt). It is always drawn because it used to exist only while something ran, which left the left flank a blank stub of black beside the right wing whenever nothing was — a blank wing beside a full one reads as something missing rather than as a state. Two channels carry "running" and either alone suffices: **tint** (orange vs dim neutral) and **motion** (turning vs held). That redundancy is required, not decorative: Reduce Motion deletes the motion, so the tint has to carry the state by itself — under it a running pill is a bright orange still ring and a quiet one a dim grey still ring (measured mean ink 0.88/0.50/0.16 lum 0.56 vs 0.38/0.38/0.38 lum 0.38), which motion alone could never give. Only `counts[.busy] > 0` can change the tint: it does not chase the per-state colours (an errored or waiting session is the badges' business, and tracking them would make the wing flicker between tints), and it stays orange while *any* session is busy, so other sessions coming and going do not blink it. The mark's *size* does not change with state, so the left flank is 130pt either way and a running/not-running transition moves nothing — the window x is untouched. And the ring does not *move* either, which is why the left flank is laid out **pinned** (`FlankAlignment.pinned(inset:)`) at `CollapsedContentView.leftContentInset` — the offset that centres the ring + running-badge pair in the 130pt wing, 37pt on the built-in display — while the right is centred. Three candidates were rendered and measured, all keeping the ring still: pinning at the outer edge (ring x 4) leaves 71pt of black between the badge and the cutout; pinning at `leftContentInset` (x 37, **shipped**) puts the pair at 37…92, i.e. centred in its wing; centring the *actual* content moves the ring 18pt on every busy↔idle transition (59 quiet → 41 running) and is rejected. Pinning at the ring-centred x instead (x 59) would centre the quiet state but push the pair to 59…114, 16pt from the cutout, i.e. off-centre in the state you actually look at. That is the one place the two flanks use different alignments, and the reason is that only the left has an always-present element whose position is a landmark. It is deliberately not the menubar's spinner: that is a *filled* disc with a wedge knocked out, i.e. the same construction as every badge glyph (`…circle.fill`), so a filled disc here would be an oversized copy of the orange badge beside it — a badge that lost its number. A hollow ring is a different shape class, so it cannot be read as one, and it lets the pill's black through its middle. CodeIsland's pixel-art mascot was rejected for the same reason the 8pt dot failed: a second drawing technique beside SF Symbols. The gap stays 90° at every size — what has to stay legible is the gap *in stroke widths* and the round caps scale with the stroke: measured on the rendered ring, the opening is **3.0 stroke widths at the shipped 12pt**, 2.5 at 11pt, 3.4 at 13pt and 3.7 at 14pt. 3.0 is the floor at which a gap still reads as an opening, 12 is the exact match, which is why it ships; 11 would be 1pt under and its gap tighter. 11pt would be 1pt *under* the glyph and its gap falls to 2.5 stroke widths, so there is no trade left to make at 12. Motion is 18° per 0.06s tick (300°/s, one revolution in 1.2s, clockwise), reusing the menubar spinner's tick interval but **not** its 45° step — and that is about the *shape*, not the size: the menubar's spinner is a filled disc with a wedge out, so its spin reads as a flicker, while this mark's 90° gap is a large high-contrast discontinuity that would lap the ring every 0.48s at 750°/s and read as a warning blink rather than a steady pulse. Three gates, all in `IslandActivityView.shouldPlay`: something running; `!NSWorkspace.shared.accessibilityDisplayShouldReduceMotion` (this is the app's **only** Reduce Motion handling — nothing honoured it before — under which the ring is shown but held at `restingAngle`, gap centred on 12 o'clock so a still mark reads as deliberate rather than stalled, and the setting is re-read on `NSWorkspace.accessibilityDisplayOptionsDidChangeNotification`); and `onScreen`, which `IslandPanel.present()`/`hide()` set, because those are the only two places the panel is ordered in or out. The timer is created in `updateMotion` when the mark starts playing and invalidated the moment it stops — **there is no timer while nothing is running**, the mark is simply drawn still, so a quiet pill costs nothing — and `tick()` re-checks the same gate so the two cannot drift. Right: the tally — **one badge per remaining state that has sessions**, most urgent first, which is `CollapsedContentView.rightBadgeOrder` = `[.error, .waiting, .idle]`: `attentionRanked`'s ranking minus the running state, which now has its own slot on the left as `CollapsedContentView.runningStatus`. So the pill's reading is two questions, not one urgency list — "is work happening + how much" (the ring and its badge, left), then "what needs me, most urgent first" (right) — and the right flank's order is still exactly the order the card sorts its rows by. `badgeStatuses` (`[runningStatus] + rightBadgeOrder`) is the one place all four states are listed, so a state cannot be forgotten by one flank while the other draws it. A badge is one tinted status glyph plus the number of sessions in that status, and every badge uses the identical construction (`CollapsedContentView.show(_:count:in:)` → `IslandMarkerGroup.badgeImage`, one point size, one gap, tabular digits). **Nothing is ever dropped**: the four states have four slots, so `maxAttentionGroups` and the whole drop-the-least-urgent rule are gone, and the pill can no longer hide an error while a less urgent state stays on show — which is exactly what the previous two-slot cap did (it drew `! n ? m` and dropped the finished count). The pill's input is one dictionary, `CollapsedContentView.counts`; the badges and the status light are both derived from it, so the mark is orange and turning exactly while the orange badge is showing and the two cannot disagree. The orange on both sides is the point, not noise: the ring is the pulse (something is happening now), the badge is the tally (how many) — the split CodeIsland makes with its mascot and its count. Content is never anchored to the cutout or the capsule edge. The **right** flank is *centred*, so a flank provisioned for three badges but holding one does not look lopsided; the cost is that a badge shifts ~18pt when a state appears there. The **left** flank is *pinned*, for the ring-landmark reason above. On a display with no cutout there is one region and one centred block, so the ring does shift there with the block — the notched case is the one the alignment decision is about. The empty pill is unreachable (`update` hides the island when there are no rows, and every row has one of the four states). This replaced two designs that failed in ways worth not repeating: a hand-drawn 8pt orange dot beside 11pt SF Symbols whose ink measures 12pt (the busiest state at 67% of its neighbours' size, sitting in the badge row where a badge was expected — drawn by separate code, which is precisely why nothing caught it), and then a glyph + count group per state capped at two, which dropped a state the pill knew about. The mark is not in the badge row at all now: other side of the cutout, the glyphs' own apparent size, no count, and a shape class no badge uses. On hover it grows into a rounded card **500pt** wide (`islandExpandedCardTargetWidth`, derived from the row's own fonts against the 200 most recent real session titles on the maintainer's machine; bounded to `0.8 × screen width` so a small display degrades instead of overflowing, floored at the collapsed capsule — now 445pt, so the floor itself binds below a ~556pt screen while the `0.8 × screen` bound binds below ~625 — and the card is only 1.12 × the pill where it used to be 1.33 ×. That ratio was never a target, only what two independent derivations produced, and the card is still sized by its *titles*: 500pt truncates none of the 200-title corpus, so widening it to restore a ratio would add black and no information, and narrowing it would cut titles to make a small pill look grander. The expansion reads through height, corner radius and alpha as well as width) listing each session as **up to three stacked lines — folder name + right-aligned age / title / context usage — never two fields on one line**, each absent line collapsing the row by exactly its own height. Row height is therefore `30 + 14 × (lines − 1)` (`islandRowHeight(lines:)`, one source of truth shared by the card layout, the height budget and the window frame), a full three-line row being 58pt. The context line is the menubar detail row's readout in white α0.5 (`12k / 200k tokens · 6%`, banded warn orange / critical red with the band glyph in the status-glyph column, placeholders at white α0.32). The list is **capped by a height budget, not a row count** (`IslandListBudget`: the smaller of 40% of the screen's usable height and the distance from the top edge to the bottom of the usable area, less chrome; each row contributes its own height), and the tail folds into an inert `+k more` row — inert because `IslandCardView.hitTest` only ever hands clicks to session rows. Folding is safe only because the list is re-ranked `error < waiting < busy < idle` (stably, in `attentionRanked`) and the first row is always taken, so a fold can never hide an error while an idle row stays on show; and a row click calls `onSelectSession(pid)` → `SessionMonitor.focusSession`. The island and the dropdown cannot drift on context usage: thresholds, wording, display mode and banding are resolved once in `Models.swift` (`ContextUsagePresentation`, `ContextBand`, `ContextDisplayMode`, `compactTokens`) and consumed by both the menu's `contextDetailItem` and `AppDelegate.islandContext` — the island only decides how to paint it on black. One latent trap fixed on the way: a non-positive `limit` is now treated as unknown rather than divided by, because the old inline maths reached `Int(Double(used)/0 * 100)` and trapped. Three non-obvious requirements, each of which was a real bug here: (1) **hover is polled**, a 0.15s `NSEvent.mouseLocation` check against the *target* rect — **not** `NSTrackingArea`, whose `.inVisibleRect` area is torn down and rebuilt by the window-resize animation, synthesising `mouseEntered`/`mouseExited` pairs while the pointer never moves (that made the island oscillate expand↔collapse forever); (2) the expand/collapse delays are **one-shot** and must be guarded (`expandWork == nil` / `collapseWork == nil`) — the poll re-runs every 0.15s, so a naive cancel-and-reschedule pushes the 0.35s deadline back on every tick and the island never expands or collapses at all; (3) the panel **must be keyable** (`canBecomeKey` true, `canBecomeMain` false) and every hit-testable view must return `acceptsFirstMouse == true` — a non-keyable non-activating panel belonging to an inactive accessory app receives no mouse events whatsoever, so with `canBecomeKey` false the pill click, the row click and the tmux jump are all silently dead while hover still works (hover only reads the cursor, it needs no events). Because it is a `.nonactivatingPanel`, becoming key does not activate the app or take the frontmost app's keyboard focus. `AppDelegate.render` pushes `[IslandRow]` to the `IslandHost` on every poll tick, which fans the one list out to every screen's panel — the push hops to the main actor (`Task { @MainActor in }`) because `render` is nonisolated while `IslandHost`/`IslandPanel` are `@MainActor`; `menuWillOpen` calls the host's `collapse()`, which collapses **all** of them; menu → "Show island" (`ocbar.island`, default on) toggles them, and with no rows (or disabled) every panel is ordered out.
- busy → idle/waiting transitions drive notifications + speech bubble. App targets OpenCode v2 only: all sessions share one `opencode serve --service` process, so no per-terminal `--port` is needed. v1 users should use tag `oc_v1`. The bubble is gated on `UserDefaults` key `ocbar.bubble` (default true, menu → "Show bubble"); with it off `showBubble` returns before both the bubble and `bounceIcon()`, since the bounce only exists to point at the bubble.
- Only root sessions (top-level, not subagent children) that are active/waiting, or already viewed with the later of last view/activity within 30 min, are shown, labeled by project folder name. Menubar shows per-session labels up to a cap (default 4, configurable 0–10 via menu → "Projects shown", UserDefaults key `ocbar.projectsShown`); at 0 it drops project names entirely and renders one glyph + count per status instead (`aggregateTitle`), most urgent first, with the busy spin still animating — **unless the island is on**, in which case the menubar drops to the plain `ocbar` name (`MenubarTitleShape.appName`) because the island already carries that detail; the VoiceOver summary keeps the counts on both paths (`aggregateSummary(statuses:)`). The shape is decided by the pure `menubarTitleShape(sessionCount:projectsShown:islandEnabled:)`, delimited by `<menubar-title-shape>` sentinel comments because an out-of-tree harness extracts exactly that block — don't delete the markers as stray comments. With no sessions the item stays the grey dot + "No OpenCode sessions" whatever the toggles say, since the island is ordered out when it has no rows.
